## 0. 背景と今回のゴール

SUKIMA は「部屋を作って URL を送るだけ」で友達と遊べる大人向け隙間時間ミニゲーム集。ゲーム自体はそろっているが、**別端末同士の実通信（Supabase Realtime）では一度も検証されていない**。実通信では、同じブラウザ内の BroadcastChannel（デモモード）では起きない「遅延・欠落・順序入れ替わり・切断・スリープ」が日常的に起きる。

今回のフェーズのゴールは次の 3 つ。

| # | ゴール | 成功の定義 |
| --- | --- | --- |
| G1 | 別端末オンライン対戦を実用品質にする | 擬似ネットワーク（遅延・欠落・切断を再現するテスト用通信層）上の自動テストで、本書の例外系 AC がすべて通る |
| G2 | 静的ホスティングで公開できる | Vercel 等に `dist/` を置き、環境変数を入れるだけで動く。手順が README にある |
| G3 | ミニゲームの難易度・テンポを調整しやすくする | 調整用の数値が 1 か所に集まり、数値を変えるだけで反映される。範囲外の値はテストで検出される |

**判断基準（PdM）**：「説明なしで数秒で遊び始められるか」を最優先。通信トラブル時も「固まった」と感じさせず、何が起きているかを一言で伝え、可能な限り自動で元に戻す。

## 2. 現状の仕組み（確認した事実の要約）

- **通信層**（`transport.ts`）：`send / onMessage / ready / close` のみ。Supabase は `sukima:<コード>` チャンネルの broadcast（`self:false, ack:false`、`eventsPerSecond: 20`）。`ready` は最初の `SUBSCRIBED` で resolve、`CHANNEL_ERROR` / `TIMED_OUT` で reject。**一度 resolve した後の切断・再接続はアプリに通知されない**（`CLOSED` も未処理）。`send` の戻り値（Promise）は `void` で捨てており、送信失敗は検知していない。なお使用中の realtime-js 2.117.3 は、未接続時の `send` を自動で REST 送信にフォールバックする（警告ログを出す）。
- **メッセージ種別**（`useRoom.ts`）：`state`（ルーム全状態）/ `action`（参加者→ホストの操作）/ `hb`（2.5 秒ごとの生存通知）/ `bye`（退出・pagehide 時）。
- **ホスト権威**：ホストは操作を `reduceRoom` に通し、変化があれば `version+1` して**全状態を毎回ブロードキャスト**。さらに 5 秒ごとに全状態を再送（resync）。
- **状態の優劣**：`compareStates` = `epoch`（ホスト世代）→ `hostId` の小さい方 → `version` の順。
- **オンライン判定**：最後に何かを受信してから 9 秒（`OFFLINE_AFTER_MS`）以内。
- **ホスト引き継ぎ**：ホストから 9 秒受信がなければ、参加順で最古のオンラインメンバーが `epoch+1` で引き継ぐ。ホストの `bye` を受けた場合は `lastSeen` が消えるので**次の 500ms tick で即座に引き継ぐ**。
- **リロード復帰**：プレイヤー ID は sessionStorage（タブ単位）。状態のスナップショットも sessionStorage に保存し、3.5 秒誰からも状態が来なければスナップショットから自分がホストとして復元する。
- **入力検証**：`msg` は `'t' in msg` と `from` だけ確認し、`state` の形も `action` の形も検証していない。
- **ゲーム進行タイマー**：ホストだけが `schedule()` の時刻で `setTimeout` し、`gameSystem` アクションを自分に適用。
- **ミニゲームラッシュ**：各端末がローカルでミニゲームを遊び、結果 `{score, success}` を `submit` で 1 回だけ送る（`MicroStage` が seed ごとに 1 回に制限）。ホストは `endsAt`（開始 + 制限時間 + 猶予 2.5 秒）で締め切り、未提出は失敗扱い。生存者全員がそろえば締め切りを「今 + 1.6 秒」に短縮。

## 3. 詳細仕様（機能ごとの振る舞い）

### F1. 通信層の接続状態（Must）

通信層は接続状態を公開し、UI はそれを表示する。

| 状態 | 意味 | UI |
| --- | --- | --- |
| `connecting` | 初回接続中 | 「接続中…」（現行どおり） |
| `connected` | 送受信可能 | 表示なし |
| `reconnecting` | 一度つながった後に切れ、自動再接続中 | 画面上部に細い帯「再接続中…」。ゲーム画面は消さない |
| `failed` | 初回接続をリトライしても失敗 | 「接続できませんでした」＋「再試行」ボタン（ページ再読み込みなしで再接続を試みる） |

- 初回接続は最大 3 回まで自動リトライ（間隔 1s → 2s → 4s 目安）。それでもだめなら `failed`。
- `connected` → 切断 → 再接続に成功したら、直ちに F3 の同期要求と未確認アクションの再送（F4）を行う。
- オフライン（`navigator.onLine === false` / `offline` イベント）を検知したら `reconnecting` を表示。`online` イベントで即再接続を試みる。
- デモモード（BroadcastChannel）は常に `connected`。

### F2. 受信データの検証（Must）

- 受信メッセージは `unknown` として受け、形を検証する純粋関数（例：`parseWireMessage`）を通す。不正なものは**黙って捨て、例外を投げない**。
  - 共通：`t` が既知の種別、`from` が空でない文字列（長さ上限あり）。
  - `state`：`code` が自部屋のコードと一致、`epoch`/`version` が有限の正の整数、`hostId` が文字列、`players` が `{id,name}` の配列（最大 `MAX_ROOM_PLAYERS`）、`chat` が配列、`game` が null かオブジェクト。
  - `action`：`RoomAction` の各種別ごとにフィールドの型を検証（例：`join.name` / `chat.text` は文字列、`setOption.value` は数値）。
- ホストはゲームの `reduce` を例外から保護する：`reduce` が例外を投げた場合、状態を変えずにそのアクションを捨てる（ゲームは続行）。
- 画面描画中にゲーム View が例外を出しても、アプリ全体が真っ白にならないよう、ゲーム領域にエラー境界を置き「表示に失敗しました（再読み込み）」を出す（Should）。

### F3. 同期要求（参加・リロード・復帰時の即時追いつき）（Must）

- 状態を持っていない端末、再接続直後の端末、タブ復帰直後の端末は「同期要求」（既存の `hb` 拡張でも新種別 `sync` でもよい）を送る。
- ホストは同期要求を受けたら、**メンバーかどうかに関わらず**直ちに最新状態を返す。ただし同じ相手への返信は 1 秒に 1 回まで。
- 目標：リロード・再接続から状態表示まで、通信遅延 + 1 秒以内（現状は既存メンバーのリロード時、最大約 5 秒待つ）。

### F4. 操作（アクション）の確実な配送（Must）

- 参加者のアクションにはプレイヤーごとの連番 `seq` を付ける（例：`{t:'action', from, seq, action}`）。
- ホストはプレイヤーごとの「処理済み最大 seq」をルーム状態に持つ（ホスト交代後も引き継がれるように `RoomState` に含める）。
  - `seq` が処理済み最大以下 → 重複・古いものとして無視。
  - それより大きい → 処理し、処理済み最大を更新（`reduce` で状態が変わらなくても更新する）。
- 参加者は送ったアクションを「未確認」として保持し、受信した状態の処理済み seq が追いつくまで約 1 秒ごとに**同じ seq のまま**再送する。未確認アクションは送信から 10 秒で破棄する（古い操作を後から適用しない）。
- 再送は順番どおり行う。ある seq より後の seq が先に処理された場合、前の seq は破棄される（＝順序入れ替わりで「古い操作が新しい操作を上書きする」ことはない）。
- ホスト自身の操作は seq 不要（ローカル即時適用）。
- これにより、ミニゲームラッシュの `submit` が一時切断で失われても、締め切り（`endsAt`）前に届けば成功として扱われる。

### F5. 送信量の制御（連打・過剰送信）（Must）

- **ホストの状態配信の間引き**：状態が連続して変わっても、配信は 1 秒あたり最大 10 回（100ms ごとに最新 1 件を送る。最後の変更は必ず送る）。Supabase の `eventsPerSecond: 20` を超えないようにする（hb・同期返信を含めて余裕を持たせる）。
- **参加者ごとの受付上限（ホスト側）**：1 人のアクションは 1 秒あたり最大 10 件まで処理し、超えた分は捨てる（`seq` は進めない＝本人が再送できる）。
- **チャット**：1 人 3 秒に 3 件まで。超過分は送信側でボタンを一時無効化し、ホスト側でも捨てる。
- **二重操作の防止（ホストのロジック側）**：
  - `startGame`：直前の開始から 1.5 秒以内の再実行は無視（「もう一度」の二度押しで二重リスタートしない）。
  - `endGame`、`selectGame`、`setOption`：同じ値の再適用は状態を変えない（現状どおり）。
- **ミニゲーム内の連打**（連打！など）はローカル処理のままで、通信には結果 1 件しか流れない（現状どおりで良い。回帰しないこと）。
- **状態サイズ**：ブロードキャストする状態の JSON は最大構成（10人・チャット 60 件・各 200 文字・大富豪 6 人中盤）で 64KB 以下に収める。

### F6. ホスト交代の堅牢化（Must）

- 交代のトリガーは現行どおり（9 秒無通信 / `bye` / 明示的な退出）。所要時間の目標：ホスト喪失から 12 秒以内に新ホストが決まり、ゲームのタイマーが再開する。
- **二重ホスト（split brain）の収束**：オンライン判定が端末ごとにずれて 2 人が同時に引き継いだ場合、`compareStates` により 3 秒以内（次の配信・resync まで）に 1 人へ収束する。負けた側がその間に受け取った操作は、F4 の再送で勝った側に届き直すこと。
- **復帰した旧ホスト**：自分より新しい `epoch` の状態を受け取ったら即座にホストをやめ、ゲームのタイマーを止める（現行の `commit → reschedule` で止まることをテストで保証する）。旧ホストのタイマー由来の操作は、他の端末で古い世代として無視される。
- **新ホストのタイマー**：引き継いだ時点で `schedule()` を再計算する。予定時刻を過ぎていれば即実行する（ラッシュで締め切りを過ぎていればすぐ結果画面へ）。
- **ホストのリロード**：ゲームは止まらず、別の人がホストを引き継ぐ（現行どおり。ホスト権を元の人に戻す必要はない）。リロードした本人は 3 秒以内に参加者として復帰する。

### F7. 参加・満員・途中参加（Must / 一部 Should）

- **満員（Must）**：11 人目が入ろうとしたら、ホストは「満員」を返す（または状態から本人が判定する）。参加者側は「この部屋は満員です（最大 10 人）」画面を出し、`join` の再送をやめる。「トップへ」ボタンあり。
- **途中参加（Should）**：ゲーム中に入った人（`game.players` にいない人）には、ゲーム領域の上に「観戦中 — 次のゲームから参加できます」と表示する。ゲーム操作は送らない（送ってもホストは無視：現行どおり）。
- **外された人（Should）**：オフライン中にホストに外され、戻ってきた人には「ホストにより部屋から外されました」と表示し、「もう一度参加する」ボタンで再参加できる（現状は「部屋を退出しました」と表示され、自分で退出したように見える）。
- **部屋が見つからない**：`connected` なのに 8 秒間ホストから状態が来ない → 「部屋 XXXX が見つかりません」。接続そのものができない場合は F1 の `failed` を出し、両者を区別する。
- **「このコードで部屋を作る」**：押したら確実にその場でホストとして部屋が作られる（現状は動作しない疑いがある。下表 E-12 参照）。

### F8. 部屋コードの衝突防止（Should）

- 「部屋を作る」時、作成者はまずチャンネルに入って 1.5 秒間、既存の部屋（他人の `state` / `hb`）がないか確認する。あれば別のコードを自動で選び直す（最大 3 回）。
- 既存の部屋に、後から作られた同じコードの部屋が上書きされてはならない。

### F9. タブ非表示・スマホのスリープ（Must）

- タブが表示に戻った（`visibilitychange` → visible、`pageshow`（bfcache 復帰）、`online`）ら、ただちに：生存通知、接続状態の確認（切れていれば再接続）、F3 の同期要求、F4 の未確認アクション再送を行う。
- 非表示中のホストは、ブラウザがタイマーを間引くため進行が遅れる・止まる可能性がある。9 秒以上ホストの通信が途絶えたら F6 で交代する（現行の仕組みで良い）。
- 非表示中のプレイヤーが参加しているラッシュのステージは、時間切れで失敗扱いになる（仕様として許容。復帰後は最新ステージから続行）。

### F10. 公開（デプロイ）準備（Must）

- `npm run build` の `dist/` を Vercel / Netlify / Cloudflare Pages / GitHub Pages に置くだけで動く。ハッシュルーティング（`#/r/ABCD`）なのでリライト設定は不要。
- README に Vercel の手順（リポジトリ連携、Build Command `npm run build`、Output `dist`、環境変数 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`、Supabase 側の Realtime 設定）を書く。
- **本番ビルドで Supabase 未設定**のときは、トップページでも「デモモード（同じブラウザ内のタブ同士のみ）」と分かる表示を出す（入れ忘れに気づけるように）。現状はルーム画面にのみバナーがある。
- 招待 URL のプレビュー用に OGP（`og:title` / `og:description` / `og:image` / `og:url` は任意 / `twitter:card`）を `index.html` に追加する（Should）。サブパス公開でも画像パスが壊れないこと。
- 秘密情報：クライアントに含めるのは anon キーのみ（現行どおり）。`.env.local` はコミットしない。

### F11. ミニゲームの調整しやすさ（Must）

- **調整値の一元化**：次の数値を 1 つのファイル（例：`src/games/micro/tuning.ts`）にまとめ、ゲーム本体はそこから読む。コメントで「大きくすると易しく/難しく」を日本語で書く。
  - テンポ：ラッシュの指示表示時間（現 2400ms）、結果表示時間（現 2500ms）、全員そろった後の判定表示（現 1600ms）、通信猶予（現 2500ms）、ひとり用の指示表示（現 2000ms）、ミニゲーム直後の判定表示（現 1500ms）、最小プレイ時間（現 800ms）
  - スピードカーブ：何ステージごとに速くなるか（現 5）、1 段階の上げ幅（現 0.15）、上限倍率（現 2.0）
  - ライフ：既定値（現 4）と選択肢（現 3/4/5）
  - 各ミニゲーム：基本制限時間 `baseMs`・速くなるか `scales`（現 `MICRO_META`）と、ゲームごとの難易度値（例：連打の目標 1 秒あたり 5 回、止めろのゾーン幅 12%・往復周期 900〜1400ms、タッチの必要命中率 60%、かぞえろの個数 5〜12・表示時間、3 秒ぴったりの許容誤差 ±250ms、ふくらませろの限界 12〜28 回・最低 10 回、文字の色/仲間はずれの正解数条件、よけろの落下間隔 など。現状は `action.tsx` / `brain.tsx` に直書き）
- **ミニゲームの有効/無効**：各ミニゲームに `enabled`（既定 true）を持たせ、false のものはラッシュとひとり用チャレンジの出題から外れる（ひとり用の「1つずつ練習」には出してもよい）。
- **ルール文言の連動**：ラッシュのルール説明「5ステージごとにスピードアップ」などの数値は調整値から生成し、数値を変えても説明と食い違わない。
- **妥当性テスト**：調整値に対して自動テストで次を検査する。
  - すべての時間は正の数。最高速度時の各ミニゲームの制限時間が 2000ms 以上（物理的に遊べる下限）。
  - 有効なミニゲームが 2 種類以上（「同じゲームが連続しない」ルールが成立する）。
  - ライフの既定値が選択肢に含まれる。
- **スコア非表示の維持**：調整しても、プレイヤーに見せる結果は「クリア / ミス」「何ステージ クリア」「勝ったか」だけ。数値スコアは表示しない（現行方針）。

### F12. 通信の自動テスト基盤（Must。QA・Backend 向け要件）

- 実際の Supabase なしで例外系を再現できる「擬似ネットワーク」を用意する：複数の仮想端末をつなぎ、端末ごとに遅延（固定/ゆらぎ）・欠落率・順序入れ替え・切断/再接続・送信失敗を設定できる。時刻は偽タイマーで進める。
- ルーム同期の処理（現在 `useRoom.ts` の中にある受信処理・tick・引き継ぎ判定）は、React に依存しない形で擬似ネットワーク上から動かせること（具体的な分割方法は CTO / Backend が決める）。
- 本書の AC のうち「自動」とあるものは、この基盤上の vitest で検証する。

## 4. 例外系の仕様

凡例：**現状** = コードを読んで確認した事実（実機未検証のものは「推定」と明記）／ **あるべき** = 今回の目標。

| ID | ケース | 現状（確認した事実） | あるべき振る舞い | 対応 |
| --- | --- | --- | --- | --- |
| E-01 | 一時的な通信切断（〜9秒） | Supabase の再接続は realtime-js 任せで、アプリは切断を知らない（`ready` は初回のみ）。切断中に送ったアクションは失われるか、REST フォールバック送信の成否が無視される。状態は 5 秒ごとの resync で追いつく。UI に変化なし。 | 「再接続中…」を表示。再接続後すぐ同期要求し、未確認アクション（10 秒以内）を再送。ラッシュの提出は締め切り前に届けば成功扱い。 | F1, F3, F4 |
| E-02 | 長時間の切断（9秒超） | 他の端末からはオフライン扱い（灰色）。ホストなら他の人に交代。本人は自分の古い状態を表示し続け、他に誰も見えなくなると 9 秒後に自分がホストを名乗る（自分だけの世代ができる）。復帰時、相手の世代が新しければ相手の状態に置き換わる。 | 本人には「再接続中…」を出し続ける。復帰時は F3 で即最新状態に追いつく。孤立中に自分がホストを名乗った場合も、復帰後 3 秒以内に正しい部屋の状態へ収束する（他人の進行を巻き戻さない）。 | F1, F3, F6 |
| E-03 | 参加者のリロード | ID は sessionStorage で維持され同一人物として戻る。ただしホストは「メンバーでない人の hb」にしか即答しないため、既存メンバーのリロードは**最大約 5 秒「接続中…」**のまま（resync 待ち）。 | 3 秒以内（擬似ネットワーク上は遅延 + 1 秒以内）に元の画面へ。ラッシュ中ならプレイ中のステージに戻り、提出済みなら結果待ち表示。 | F3 |
| E-04 | ホストのリロード | `pagehide` で `bye` が送られ、他の端末は次の tick（≤0.5 秒）で次の人がホストを引き継ぐ。リロードした本人は参加者として戻る。誰もいなければ 3.5 秒後にスナップショットから自分がホストとして復元。 | ゲームは止まらず続行（現行の方向性で良い）。本人は 3 秒以内に復帰。ひとりだけの部屋でも状態を失わない。 | F3, F6 |
| E-05 | ホストがタブを閉じる / 退出ボタン | 退出ボタン：オンラインの次の人へ `epoch+1` で譲った状態を送ってから抜ける。閉じる：`bye` で即交代。`bye` が届かない（電池切れ等）場合は 9 秒後に交代。 | 現行どおり。いずれの場合も 12 秒以内にゲームのタイマーが再開する。 | F6 |
| E-06 | 二重ホスト（同時引き継ぎ） | 各端末のオンライン判定がずれると 2 人が同じ `epoch` で引き継ぎうる。`hostId` の小さい方が勝ち、負けた側は勝った側の状態を受けて収束（仕組みはある、テストなし）。負けた側が受けた操作は失われる。 | 3 秒以内に 1 人に収束。負けた側に送られた操作は再送で勝った側に届く。 | F4, F6 |
| E-07 | 旧ホストの復帰（スリープ明け等） | 新しい世代の状態を受け取ると `commit` → `reschedule` でホストでなくなりタイマーも止まる。旧ホストが復帰直後に古い状態を resync しても、他の端末は世代が古いので無視し、新ホストが最新状態を送り返す。 | 現行の挙動をテストで保証する。 | F6 |
| E-08 | 同時操作・重複操作 | 「もう一度」の連続タップで `startGame` が 2 回適用されうる（2 回目でゲームが再初期化される）。参加者の操作に重複検出はなく、再送の仕組みもないため重複自体は起きにくいが、届かなければ消える。 | `startGame` は 1.5 秒以内の再実行を無視。参加者の操作は seq で重複排除（再送しても 1 回だけ適用）。 | F4, F5 |
| E-09 | 連打・過剰送信 | ミニゲーム内の連打はローカル処理で通信は結果 1 件（良好）。一方、ホストは状態が変わるたびに全状態を即ブロードキャストするため、10 人が同時に操作すると瞬間的に多数の配信が発生。Supabase クライアントは `eventsPerSecond: 20`。チャットの送信回数制限なし。 | ホストの配信は 100ms 間引き（1 秒最大 10 回）。1 人あたりの受付上限 10 件/秒、チャット 3 件/3 秒。 | F5 |
| E-10 | 遅延・順序入れ替わり・欠落 | 状態は `epoch/version` 比較で古いものを捨てる（順序入れ替わりに強い）。アクションは届いた順に処理、欠落は検知不能。時計はホスト時刻との差の推定（遅延最小サンプル）を使う。ラッシュは締め切りに 2.5 秒の猶予あり。 | アクションは seq で重複排除＋再送、古い seq は破棄。状態は現行方式を維持。遅延 500ms・欠落 20% の擬似ネットワークでもラッシュ 10 ステージが全員同じ結果で進行する。 | F4 |
| E-11 | 満員（11人目） | `join` は無視される。本人は状態を受け取ると `ready` になり、**メンバー一覧に自分がいないままロビーが見え**、状態を受けるたびに `join` を送り続ける。満員の表示なし。 | 「この部屋は満員です」画面を表示し、`join` を止める。 | F7 |
| E-12 | 部屋が見つからない／「このコードで部屋を作る」 | 8 秒で「見つかりません」。ただし接続自体ができない（`ready` が解決しない）場合も「見つかりません」になり区別できない。「このコードで部屋を作る」は `location.hash` を同じ値に設定するだけなので `hashchange` が起きず、**何も起きない（推定、実機で要確認）**。 | 接続失敗と部屋なしを区別。「このコードで部屋を作る」で確実にホストとして部屋ができる（F8 の衝突確認つき）。 | F1, F7, F8 |
| E-13 | 部屋コードの衝突 | コードは 31 文字×4 桁のランダム（約 92 万通り）で重複確認なし。同じコードで作ると同じ `epoch=1` の状態がぶつかり、`hostId` の小さい方が勝つため、**既存の部屋が新しい部屋に上書きされうる**。 | 作成前に既存の部屋を確認し、あれば別コードにする。 | F8 |
| E-14 | 途中参加 | `join` でメンバーに追加され、ゲームは観戦（`game.players` は開始時のまま。ゲーム操作はホストで無視）。観戦中である旨の共通表示はない（ラッシュは「観戦中」表示あり、他ゲームは View 次第）。 | 共通の「観戦中 — 次のゲームから参加できます」表示。「もう一度」でオンラインのメンバーとして参加。 | F7 |
| E-15 | オフライン中に外された人の復帰 | 自分のいない状態を受けると「部屋を退出しました」画面。自分で抜けたように見える。 | 「ホストにより外されました」＋「もう一度参加する」。 | F7 |
| E-16 | タブ非表示・スマホのスリープ | 表示に戻ると `hb` を 1 回送るのみ。状態は最大 5 秒後の resync で追いつく。iOS 等で JS が止まるとホストは 9 秒後に交代される。非表示のホストはタイマー間引きでゲーム進行が遅れうる。 | 表示復帰・bfcache 復帰・online 復帰で、生存通知＋再接続確認＋同期要求＋未確認アクション再送。2 秒以内に最新状態。 | F9 |
| E-17 | Supabase 接続失敗 | 初回 `CHANNEL_ERROR` / `TIMED_OUT` で即「接続できませんでした」。「再試行」はページ再読み込み。接続後のエラーは無視。 | 初回は 3 回まで自動リトライしてから `failed`。接続後のエラーは `reconnecting` 表示で自動復旧を待つ。「再試行」は再読み込みなしで再接続。 | F1 |

## 7. 受け入れ条件（Acceptance Criteria）

全 AC 共通：`npm run typecheck` / `npm test` / `npm run build` が成功すること。
