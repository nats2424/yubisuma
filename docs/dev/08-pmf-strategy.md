## 1. SUKIMA にとっての PMF

### 1.1 定義

> **「仲のいいグループが、集まったときに『SUKIMA やろう』と自分たちから言い出し、誰かが URL を貼る」が、運営の働きかけなしに繰り返し起きている状態。**

SUKIMA の価値は「ひとりの熱狂」ではなく「グループの場が温まること」なので、単位は**ユーザーではなくルーム（＝1 回の集まり）**で見る。PMF の判定は、次の 4 つが**同時に**、Phase 1 の母集団（〜100 ルーム）で 4 週間続いていること。

| # | 条件 | 初期の閾値（仮） | なぜこの条件か |
| --- | --- | --- | --- |
| P1 | 遊ばれたルームで、**2 ゲーム以上**遊ばれた割合 | 50% 以上 | 1 ゲームで終わる＝「試しただけ」。もう 1 回・別ゲームが選ばれれば、その場で価値があった |
| P2 | ホストのうち、**7 日以内に再びホスト**した割合（再ホスト率） | 25% 以上 | 「次の機会に思い出す」が起きているか。飲み会の頻度（週 1 未満が多い）を考え 7 日と 28 日の両方を見る（28 日は 40% 以上） |
| P3 | 新規ホストのうち、**以前ゲストとして参加したことがある**割合 | 20% 以上 | ゲストが別のグループで幹事になる＝URL によるバイラルが自走している |
| P4 | 試遊・アンケートで「SUKIMA が使えなくなったら**とても残念**」と答えた人の割合（Sean Ellis テスト） | 40% 以上（回答 30 人以上） | 行動指標を補う定性の裏付け |

### 1.2 北極星指標

> **週あたりの「楽しまれたルーム」数** ＝ 3 人以上がゲームに参加し、かつ 2 ゲーム以上遊ばれたルームの数（週次）

- 「部屋作成数」では試しに作って誰も来なかった部屋も数えてしまう。「参加者数」では 1 回の飲み会が大きく数えられるだけ。**人が集まり（招待が機能し）、続けて遊んだ（体験が良かった）**の両方が入る数にする。
- ひとり用（ケンジ）は北極星に含めない。ひとり用は「知る・試す・広める」の入口として先行指標で見る（§1.3 L5）。
- 2 人ルーム（カップル・家族）は、遊べるゲームが限られるため別集計で見る（P1〜P3 の母集団からは外さない）。

### 1.3 先行指標

| ID | 指標 | 定義（計測イベントは §2.3） | 初期の目標（仮） | 見ている段階（07） |
| --- | --- | --- | --- | --- |
| L1 | 1 ルームあたりの遊ばれたゲーム数 | `game_start` 数 / `game_start` が 1 回以上あったルーム数（中央値と分布） | 中央値 2 以上 | 結果 → もう 1 回 |
| L2 | 招待 URL からの参加率 | 招待経由の `join_view` のうち `joined` に至った割合 | 85% 以上 | 開く → 参加 |
| L3 | 招待 1 回あたりの参加人数 | `invite_share` があったルームの、ホスト以外の参加者数 | 2.5 人以上 | 招待 → 集まる |
| L4 | 7 日以内の再ホスト率 | `room_create` 時に「直近 7 日にこの端末でホストしたか」の真偽（端末内で判定して送る。§2.1） | 25% 以上（P2） | 再訪 |
| L5 | ひとりで挑戦 → 部屋作成への転換 | `practice_over` を出した端末のうち、7 日以内に `room_create` した割合（端末内判定） | 10% 以上 | 広める |
| L6 | ルーム参加者数の分布 | `game_start` 時の参加人数（1 / 2 / 3〜4 / 5〜6 / 7〜10 のバケット） | 3〜6 人が 60% 以上 | H1・H2 の検証 |
| L7 | 部屋を作ったが誰も来なかった割合 | `room_create` から 10 分以内にホスト以外の参加がなかったルーム | 30% 以下 | 招待の失敗 |
| L8 | ゲームごとの「続けて遊ばれた率」 | そのゲームの直後に `game_start`（もう一度 or 別ゲーム）が続いた割合 | ゲーム間の比較に使う | ラインナップ判断 |
| L9 | 接続失敗率 | `room_view` のうち `conn_failed` / `room_notfound` になった割合 | 5% 以下 | 技術的な健全性（実機の品質） |

## 2. サーバーなし構成での最小計測

### 2.1 方針

- **個人を特定しない**：名前・チャット・部屋コード・IP の保存・端末をまたいで追える ID は送らない。Cookie を使わない。
- **端末の中で判定して、結果だけ送る**：再ホスト率・ひとり→部屋の転換は、端末の `localStorage` に「最後にホストした日」「最後にひとり用を遊んだ日」を置き、イベントに `rehost7d: true` のような**真偽値だけ**を載せる。端末 ID を送らずに率が出せる。
- **ルーム単位の集計は使い捨ての ID で**：ホストが部屋を作るたびにランダムな `rid`（部屋コードとは無関係）を作り、ルーム状態に載せずにホストの端末だけが持つ。ホスト交代後は新ホストが別の `rid` で送る（ルームが 2 つに見えるのは許容し、`host_takeover` イベントで補正）。
  - ゲストのイベント（`join_view` / `joined`）には `rid` を付けない（ゲストは知らないため）。L2 は全体の割合で見る。
- **送るのはホストの端末中心**：ルームの事実（人数・ゲーム開始）はホストが一番正しく知っている。ゲストのイベントは参加まわりだけ。
- **コードはホスト権威の純粋関数に入れない**：計測の呼び出しは `src/components/` と `useRoom.ts` の配線層に置き、`logic.ts` / `engine.ts` を汚さない（CLAUDE.md の規約）。

### 2.2 ツール候補（CTO・Security と選定）

| 候補 | 何ができるか | 費用感（要確認） | 評価 |
| --- | --- | --- | --- |
| **Umami Cloud**（または自前ホスト） | Cookie なし、カスタムイベント＋プロパティ、ハッシュ遷移を手動送信 | 無料枠あり（月のイベント数上限あり） | **第一候補**。イベント設計どおりに測れる。自前ホストならデータを手元に置ける |
| Plausible | Cookie なし、カスタムイベント＋プロパティ、EU ホスト | 有料（月 9 ドル程度〜） | 機能は十分。費用がかかる |
| GoatCounter | Cookie なし、ページビュー中心、イベントは「パス」として送る | 非商用は無料 | プロパティが弱く、L1 の分布などは工夫が要る |
| Cloudflare Web Analytics / Vercel Web Analytics | ページビュー中心 | 無料〜（Vercel のカスタムイベントは有料プラン） | 流入元・端末比率だけなら十分。イベントは弱い |
| 自前（Supabase Edge Function や Cloudflare Worker に `sendBeacon`） | 何でも | ほぼ無料 | 「サーバーなし」の方針から外れる。PMF 前はやらない |

**PdM 推奨**：Umami Cloud の無料枠で開始。上限に近づいたら（＝それ自体が良い兆候）有料か自前ホストに移る。導入前に Security レビュー（読み込むスクリプトの出どころ・CSP・送る項目の確認）と、トップの下部に「匿名の利用統計を取っています（名前・チャット・部屋コードは送りません）」の一文を出す。

### 2.3 計測イベント設計（最小）

共通プロパティ：`dev`（`sp` / `pc`。`pointer: coarse` で判定）、`mode`（`online` / `demo`。demo は集計から除外）、`v`（アプリの版）。

| イベント | 送る端末・タイミング | プロパティ | 使う指標 |
| --- | --- | --- | --- |
| `page_view` | 各ルート表示時（`home` / `practice` / `room`） | `route`、`ref`（`invite` = ルーム URL から直接 / `direct`） | 流入 |
| `room_create` | ホスト：部屋を作ったとき | `rid`、`rehost7d`、`rehost28d`、`was_guest`（この端末で過去にゲスト参加したか）、`from`（`home` / `practice` / `notfound`） | L4・P2・P3・L5 |
| `invite_share` | ホスト：「招待する」を押したとき | `rid`、`method`（`share` / `copy` / `line`）、`players`（その時点の人数） | L3・L7 |
| `join_view` | ゲスト：参加画面または自動参加の開始時 | `named`（名前が保存済みだったか） | L2 |
| `joined` | ゲスト：初めて部屋の状態を受け取ったとき | `ms`（開いてから入室までの時間、バケット） | L2 |
| `game_start` | ホスト：ゲーム開始時 | `rid`、`game`、`n`（人数バケット）、`seq`（このルームで何ゲーム目か）、`again`（もう一度か別ゲームか） | 北極星・L1・L6・L8 |
| `game_end` | ホスト：結果画面に入ったとき | `rid`、`game`、`dur`（分、バケット） | L8 |
| `room_close` | ホスト：`pagehide` 時に `sendBeacon`（届かないこともある前提） | `rid`、`games`（遊ばれたゲーム数）、`peak`（最大人数） | L1 の補助 |
| `host_takeover` | 新ホスト：引き継いだとき | `rid`（新） | ルームの重複補正 |
| `practice_start` / `practice_over` | ひとり用 | `stage`（バケット：1〜4 / 5〜9 / 10〜14 / 15+）、`best`（自己ベスト更新か） | L5・ひとり用の継続 |
| `practice_share` / `practice_to_room` | ひとり用の共有・「友達と勝負する」（07 J-05・J-06 実装後） | — | L5・拡散 |
| `conn_failed` / `room_notfound` | 該当画面を出したとき | `dev` | L9 |
| `feedback` | 結果画面の 1 タップ感想（「また遊びたい / ふつう / いまいち」）。任意 | `game`、`answer` | 定性の補助 |

イベント総数の見積り：1 ルームあたり 10〜20 件。Phase 1（〜100 ルーム）なら月数千件で、どの無料枠にも収まる見込み。

### 2.4 計測以外で取るもの

- **試遊の観察**（Phase 0）：同席して、URL を受け取ってから参加するまでの迷い・最初の笑いが起きた瞬間・「もう 1 回」が出たかを記録する（観察シートは Phase 0 開始時に PdM が作る）。
- **短いアンケート**（Google フォーム等。トップ下部と結果画面から任意で）：Sean Ellis テスト（P4）、どのシーンで使ったか、誰と、何人で、次も使うか。
- **SNS の言及**：X で「SUKIMA」「スキマ ミニゲーム」を週 1 回検索して記録する。

## 5. 獲得・拡散戦略

### 5.1 URL 共有によるバイラル（K 係数の考え方）

SUKIMA は 1 ルームで必ず 2〜5 人の新しい人に届く。ただし**ゲストが増えるだけでは広がらない**。広がるのはゲストが別のグループで幹事になったとき。

```
K（ホスト単位） = 1 ルームあたりの新規ゲスト数 × ゲストが 30 日以内に自分でホストになる確率
例：3.0 人 × 10% = 0.3
```

- K < 1 なので、単独では自走しない（パーティーゲームの典型）。**目標は Phase 1 で K = 0.3、Phase 2 で 0.5**。残りは SNS・幹事向けの訴求で補う。
- K を上げるレバーは 2 つ：
  1. **新規ゲスト数**（招待の質）：07 J-01 OGP、J-03 共有文、J-02 招待カード、J-12 LINE で送る
  2. **ゲスト→ホストの転換**：07 J-13（ゲストの結果画面に「自分でも部屋を作れる」）、J-05（記録共有。ひとり用経由の転換）、J-11（サイト名を覚えてもらう）
- 測り方：P3（新規ホストのうち `was_guest` の割合）× L3（ルームあたりゲスト数）で近似する。

### 5.2 OGP・招待導線

- OGP 画像（全部屋共通）：案B のロゴ＋ゲームアイコン列＋「URLを送るだけで、すぐにみんなで。」「登録不要・タップで参加」。中央 630×630 に要素を収め、LINE の小さいサムネイルでも潰れないこと（06 §5.2）。
- ハッシュ URL（`#/r/ABCD`）は OGP のクローラーに部屋を区別されないため、**部屋ごとの画像（「ユウキさんが待っています」）は出せない**。出すにはサーバー側の仕組みが要るので PMF 前はやらない。
- 共有文はゲーム名を入れる：「SUKIMA でワードウルフやろう！タップで参加（登録不要）部屋コード K7MQ」。

### 5.3 SNS（X・TikTok）：「失敗が笑える」短尺動画

- 中身：ラッシュの瞬間ミニゲームで大人が真剣に失敗する 15〜20 秒（「ふくらませろ！」で割る、「3秒ぴったり！」で外す、「文字の色は？」で引っかかる）。画面録画＋手元か表情。字幕必須（音なしで見られる前提）。
- 形式を 3 種類試す：① 画面だけ（ゲームの分かりやすさ）② 飲み会の手元（シーンの想起）③ ひとり用の「何ステージ行ける？」の挑戦（真似されやすい）。各 4 本以上投稿して H9 で判定。
- 投稿ごとに `#/?s=<投稿ID>` を付け、`page_view` で流入を数える。
- 避けること：特定の人をいじる・下品なノリ（06 §4.2）、ガチャ風・煽りのサムネイル。

### 5.4 どのシーンから攻めるか

| 順 | シーン | 理由 | 主な打ち手 |
| --- | --- | --- | --- |
| 1 | **飲み会・集まりの待ち時間（SC-1）** | 06 の最優先シーン。全員が同じ場所にいるので「話す系」も成立し、ゲーム数（L1）が伸びやすい。人数 3〜6 人で招待の効果が最大。**12 月の忘年会シーズン**が Phase 1〜2 に重なる | OGP・共有文、動画②、「忘年会の待ち時間に」訴求 |
| 2 | 年末年始の帰省（SC-5） | 年に 1 回だが、世代をまたいで広がる（親戚が自分のグループに持ち帰る）。子どもが混ざると反射神経・ラッシュが強い。時期が明確で準備しやすい | 12 月下旬に「帰省のこたつで」訴求、指スマ・ラッシュを前面に |
| 3 | リモート会議前（SC-2） | 平日昼に繰り返し起きるので頻度は高いが、職場での導入には心理的なハードル（上司の目）がある。H2 で PC 比率が高ければ繰り上げる | Slack に貼る導線、「会議前 3 分」訴求、多数派ゲーム推し |

## 7. マネタイズ（PMF 後の論点）

PMF 前は**やらない**。論点だけ残す。

- **広告**：体験を壊すリスクが高い。06 §4.2 で「課金・広告があると誤解され開いてもらえない」としており、招待を受け取ったミサキが最初に見る画面に広告があると参加率（L2）が落ちる。入れるとしてもトップの下部・ひとり用のゲームオーバー画面だけにして、ルーム内（ロビー・ゲーム・結果）には出さない。
- **買い切り・サポーター**：「応援する（投げ銭）」で広告なし・限定ミニゲーム・季節パック。数値スコアなしの方針と相性が良い。
- **法人・イベント向け**：リモートワークのアイスブレイク（S1）で、独自お題のワードウルフ・多数派を作れる有料機能。H2 の結果次第。
- 判断材料：Supabase の費用がルーム数に比例して増える（§9.1）ので、Phase 2 の終わりに「1 ルームあたりの通信費」と「支払い意欲（アンケート）」を比べる。

## 8. やらないこと（PMF 前）

| やらないこと | 理由 |
| --- | --- |
| アカウント・ログイン・フレンド機能 | 「登録不要」が最大の価値。再訪は端末内の記憶と新作で作る |
| ランキング・ポイント・数値スコアの拡充 | 方針（数値スコア非表示）に反する。ガチ勢向けになりライト層が離れる |
| 知らない人とのマッチング（公開ロビー） | ターゲットは既存の友人グループ。治安対策（通報・モデレーション）の負担が大きく、サーバーも要る |
| ネイティブアプリ | ブラウザで URL を開くだけ、が招待の強み |
| サーバー・DB の導入（部屋の保存、部屋ごとの OGP、自前の計測サーバー） | 「サーバーなし」で運用コストを抑える構成を、PMF 前に崩さない |
| 有料広告・インフルエンサー施策 | PMF 前に買った流入は体験の評価を濁らせる。まず自然な紹介で P1〜P3 を測る |
| 「じっくり」系の大型ゲームの追加 | 開発コストが高く、隙間時間の価値検証に寄与しにくい。大富豪の利用率（L8）を見てから |
| 多言語化 | 日本語・LINE 文化を前提に検証する |
| 不正対策の強化（開発者ツールでのお題の覗き見など） | 友達同士で遊ぶ前提（README）。PMF 前は許容リスクとして明記する |

### 9.2 プロダクトオーナーに判断してほしい点

1. **PMF の定義と北極星の承認**：「週あたりの楽しまれたルーム数（3 人以上・2 ゲーム以上）」を北極星とし、§1.1 の P1〜P4 を PMF 判定に使ってよいか。閾値は仮置きで、Phase 0 後に見直す前提。
2. **最小計測の導入可否**：Cookie なし・個人を特定しない匿名イベント（§2）を入れてよいか。入れない場合、PMF は試遊とアンケートだけで判断することになり、P2・P3・L5 は測れない。
3. **Phase 0 の着手と期間**：Supabase 本番プロジェクトの作成、実機確認（AC-M1〜M4）、試遊 5 グループを 2〜3 週で行うこと。試遊グループの手配（PO・チームの知り合い）への協力。
4. **07 の Must 8 件を公開前に入れること**（うち 6 件は S 工数）。特に J-01 OGP の画像制作（Designer・Marketing）の着手。
5. **Supabase の費用**：Phase 1 は無料プランで開始し、使用量が上限の 70% に達したら有料プランへ移行する、という条件付きの事前承認。
6. **許容リスク**（U3）：QA-BUG-03 と「開発者ツールでお題が見える」を、Phase 1（限定公開）では許容リスクとして受け入れるか。
7. **攻めるシーンの順番**：飲み会（SC-1）→ 帰省（SC-5）→ リモート会議前（SC-2）でよいか。12 月の忘年会・年末年始に Phase 1 を間に合わせるかどうか（間に合わせるなら Phase 0 を 11 月中に終える必要がある）。
8. **数値表示の扱い**（07 J-21）：多数派の pt・反射神経の ms を残すか。PdM 案は「反射神経の ms は残す（笑いのネタ）、多数派は『当たり n 問』にする」。
